# 10 · 模型調度守則

> 最後更新：2026-07-04｜原因：初版
> 型號、effort 合法值、agent 欄位以 `05-environment.md` 為準；本檔只寫「怎麼用」。
> 本檔所有門檻都是數字。覺得門檻不合理，把證據寫進 LESSONS.md，照 `40-maintenance.md` 調整；
> 不要在單一 session 裡「這次先例外」。

## 1. 總則：指揮官不下場

主對話（指揮官）只做六件事：**拆解任務、寫派工單、讀回報、做決策、彙整落檔、與使用者溝通**。
以下動作出現任何一項，一律派 subagent，主對話只收結論：

| 動作 | 門檻 | 派給誰（見第 8 節） |
|---|---|---|
| 讀檔案 | 超過 2 個檔，或單檔超過 200 行 | scout（找位置）/ general-purpose（要消化內容） |
| 搜尋 | 一次 Grep 沒直接命中，需要換 pattern | scout 或 Explore |
| 網頁/文件研究 | 任何一次 | general-purpose；查 Claude Code 或 API 事實用 claude-code-guide |
| 改檔案 | 超過 2 個檔；超過 5 個檔另須先 1 檔試點（見 00 診斷第 3 名） | implementer |
| 跑測試/長指令並分析輸出 | 輸出預期超過 50 行 | implementer 或 general-purpose |

**允許自己做的**：已知位置的單一事實查找（一次指定行號範圍的 Read、一次命中的 Grep）、
1–2 個檔案的小修改、git 操作、寫派工單與落檔。例外：git 指令輸出預期超過 50 行
且需要逐條分析（例如翻 log 找某次變更）時，仍適用上表「跑測試/長指令」那列。

**判斷不準時的預設**：派出去。派錯的成本（一個便宜 subagent）遠低於主對話灌爆的成本。

## 2. 機型選擇表

| 情境 | model | 理由 |
|---|---|---|
| 模式已定的機械性工作：批次套用已驗證的修改、格式轉換、簡單搜尋定位 | `haiku` | 便宜，錯了升級也快（見第 6 節） |
| 預設：實作、重構、研究、消化文件、審查初審 | `sonnet` | 工作馬；**沒把握選哪個就選這個** |
| 跨模組設計、sonnet 卡關升級、對抗審查、高風險判斷的第二意見 | `opus` | 貴，只用在 sonnet 證實不夠的地方 |

## 3. effort 選擇表

| 情境 | effort |
|---|---|
| 機械性、模式已定 | `low` |
| 一般實作與研究 | `medium`（預設，不確定就用這個） |
| 驗收、審查、除錯、任何「漏掉一條就白做」的任務 | `high` |
| 升級到 opus 的卡關任務、對抗審查 | `high` 或 `xhigh` |

設定方式：用本 repo 預定義 agent（frontmatter 已設好），或 session 層級用 `/effort`。
派給內建 agent type（無 effort 可設）時，在派工單內寫明「逐項檢查、不要抄捷徑、寧可慢」
等具體行為要求代替。

## 4. 派工三件套（缺一不派）

每張派工單必含三個區塊，可直接套 `30-delegation-templates.md` 的模板：

1. **目標與動機**：做什麼＋為什麼＋產出會被怎麼用（一到三句）。
   沒有動機，subagent 遇到模糊處只能亂猜方向。
2. **驗收條件**：列點、可機械判定（fresh-context 第三方能逐條打勾的那種）。
   「找出所有呼叫點並附 file:line」可判定；「好好整理一下」不可判定。
3. **回報格式**：直接引用第 5 節的回報合約，或用模板內建的格式。

**會動到檔案的派工**（實作、重構、批次套用）必加第四項——**範圍**：只准動哪些檔案、
明確不動哪些。implementer 收到缺範圍的派工單會退回，不會開工。

**反例（禁止照這樣派）**：「幫我看一下 auth 模組有沒有問題」——沒有動機（看什麼問題？）、
沒有驗收（怎樣算看完？）、沒有格式（回什麼？）。subagent 會回一篇散文，你還得再派一次。

## 5. 回報合約（subagent 的產出規格）

subagent 回報**只准**含以下欄位，總長度以 30 行為上限：

- **結論**：≤10 行，直接回答派工單的目標
- **關鍵位置**：`檔案路徑:行號` 列表（每個論斷都要有出處）
- **未解事項與信心**：沒查到的、不確定的，明說；禁止用猜測填補
- **長產物**：寫到指定路徑的檔案裡，回報只給路徑——**禁止把整檔內容貼回主對話**

找不到就回「找不到＋已試過哪些方法」，這是合格回報，不是失敗。

## 6. 升降級路徑

```
haiku ──錯 1 次──▶ sonnet ──同一子任務連錯 2 次──▶ opus ──連錯 2 次──▶ 停，問使用者
                     ▲
  已解出的模式────────┘（寫成明確步驟後，降回 haiku/sonnet 批次套用）
```

- **haiku 錯 1 次直接升級**，不重試 haiku：它錯通常代表任務不夠機械，重試是浪費。
- **sonnet 升 opus 必附完整失敗軌跡**：做了什麼、關鍵輸出、為什麼判定失敗。
  沒有軌跡的升級會讓 opus 重走一遍同樣的死路。
- **降級**：opus/sonnet 解出的模式，寫成「不需判斷、只需執行」的步驟清單，
  降回便宜模型批次套用；先 1 個試點驗證，通過再全量。
- **同一條路徑（同方法＋同模型）最多嘗試兩次**（haiku 只嘗試一次）。第二次仍錯，
  禁止原樣再試第三次——照上方門檻升級，或換路（判準見 `20-judgment.md` 第 4 節）。
- 「錯」的定義：驗收不過、產出跑不起來、或回報被抓到與事實不符。
  不含環境暫時性失敗（網路逾時等）——那個原地重試，不計次。

## 7. 併發與隔離

- 互相獨立的子任務，**同一則訊息一次派出**平行跑；不要一個等完再派下一個。
- 兩個以上 subagent 會改到檔案時：改**不同**檔案 → 可平行；可能改**同一批**檔案 →
  序列化，或各給 worktree 隔離（Agent 工具的 `isolation: "worktree"`）。
  判斷不準 → 序列化，慢但不會撞。
- 唯讀任務（搜尋、研究、審查）永遠可以平行。

## 8. 本 repo 預定義 agent（.claude/agents/）

| agent | model/effort | 用途 | 硬限制 |
|---|---|---|---|
| `scout` | haiku / low | 找檔案、找定義、找呼叫點、確認某事物存在與否 | 唯讀；只回位置與一句摘要，不解讀 |
| `verifier` | sonnet / high | fresh-context 驗收（見第 9 節） | 唯讀；只給驗收條件與產出位置，不給實作過程 |
| `implementer` | sonnet / medium | 範圍明確的實作與修改 | 只動派工單「範圍」內的檔案 |

這些名字若不在當前 session 的 agent type 清單裡（環境沒載入本 repo 的 .claude/），
退回用 `general-purpose` 並在派工單裡貼上對應的硬限制與回報合約。
消化大量內容、網頁研究、複雜多步任務：直接用 `general-purpose`（必要時 model 指定 opus）。

## 9. 驗證不自驗

**實作者不驗收自己的產出，指揮官也不憑實作者的自述宣告完成。**

- 驗收一律派 fresh-context agent（新開的 verifier）：**只給**驗收條件與產出位置，
  **不給**實作過程與實作者的說法——避免驗證者被實作者的敘事帶著走。
- 按產出類型選驗法：
  - **檔案/文件** → read-back：驗證者實際 Read 檔案，對照驗收條件逐條打勾。
  - **程式碼** → 測試或實跑：能跑就跑，貼關鍵輸出；跑不了要寫明原因，並降級為 read-back＋
    靜態檢查，同時在回報中標註「未經執行驗證」。
  - **高風險判斷**（不可逆操作前的決策、對外發佈的內容、會被長期沿用的制度）→
    第二意見：換一個模型或角度再判一次；或產 2–3 個候選答案派評審選優。
- 驗證者回報格式：逐條 `PASS/FAIL + 證據`。證據必須是驗證者**自己讀到或跑到**的
  （file:line、指令輸出），引用實作者的說法不算證據。
- FAIL 的處理：回給原實作者修（附 FAIL 明細），修完**再驗一次**；連兩輪 FAIL 走第 6 節升級。
