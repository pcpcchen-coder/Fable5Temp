# 40 · 維護協議（改本 repo 制度檔之前，把本檔讀完）

> 最後更新：2026-07-04｜原因：初版
> 本 repo 的制度檔是「未來每個 session 的行為來源」。改它比改程式碼風險高：
> 程式碼改壞了測試會抓，制度改壞了要好幾個 session 之後才會顯形。所以維護有分級。

## 1. 權限分級

### 可以自行改（不必問使用者，但要走第 3 節流程）
- `LESSONS.md`：追加條目（這是預設動作，踩坑不寫才是違規）
- `05-environment.md`：更新**已查證**的環境事實（附來源與日期）；刪除已確認失效的條目
- `30-delegation-templates.md`：增補範例、修填空說明（不改模板的必填結構）
- 所有檔案：錯字、失效連結、路徑更名的同步修正
- CLAUDE.md：**只准**因應新增制度檔而加一行路由（仍受 80 行上限約束）

### 要先問使用者（AskUserQuestion，附你的建議與理由）
- 刪除或反轉任何既有規則（包括「放寬」——放寬也是反轉）
- 修改 CLAUDE.md 的三條紅線、或路由表以外的任何段落
- 修改升降級門檻的數字（10 號檔第 6 節）、指揮官不下場的門檻（10 號檔第 1 節）
- 新增任何「每個 session 都會固定載入」的內容（會拉高所有未來 session 的固定成本）
- 新增制度檔（先問：這能不能只是 LESSONS 的一條？見第 2 節）

**判斷不準時的預設**：當成要問的等級。制度檔改錯的代價是跨 session 的。

**使用者不在場（自主／排程 session）或環境沒有提問工具時**：「要先問」等級的變更
一律不做。把提案（動機、建議內容、理由）寫成 LESSONS.md 的一條（標籤：提案），
留給使用者裁決；然後繼續做不受此阻塞的其他工作。

## 2. 內容的升級路徑（防止制度增生）

新東西想寫進制度，走這條路，不准跳級：

```
踩坑 → LESSONS.md 一條（當下就寫）
     → 同類教訓累積 3 條 → 升級成 10/20/30 號檔的一條規則（引用來源日期），
        原條目標記「規則化：已寫入 X 檔」
     → 規則多到該檔超過 250 行 → 拆分或精簡（要先問使用者）
```

**預設答案是「先進 LESSONS」**。直接往規則檔加新規則，需要的證據是「這問題重複發生過」，
一次性的坑進 LESSONS 就夠了。

## 3. 每次修改制度檔的流程（五步，不可跳）

1. **備份點**：`git status` 確認乾淨；不乾淨先 commit
2. **改**：一次 commit 只改一個主題（方便單獨 revert）
3. **read-back**：改完實際重讀改動段落，確認寫的是想寫的
4. **複述測試**（只要改了規則語意就必做）：派一個 fresh-context agent 只讀改後的檔案，
   要求它回答「這條規則要我在什麼情況下做什麼」；複述錯 → 規則有歧義，改到複述對為止
5. **commit + push**：訊息寫「動機」而非「改了什麼」（diff 已經說了改了什麼）；
   若規則語意有變，順手更新該檔檔頭的「最後更新」行

## 4. 精簡觸發條件（任何 session 看到就有義務處理）

| 觸發 | 動作 | 要問使用者嗎 |
|---|---|---|
| CLAUDE.md 超過 80 行 | 把內容抽到引用檔，CLAUDE.md 留路由 | 不用（這是紅線的執行） |
| LESSONS.md 超過 30 條或 250 行 | 把重複教訓規則化，已規則化條目移到 `LESSONS-archive.md` | 不用 |
| 任一規則檔超過 250 行 | 提出精簡或拆分方案 | 要 |
| 兩條規則互相矛盾 | 立刻停用其一：在較新的那條旁標註衝突、在 LESSONS 記一條，提交使用者裁決 | 要 |

## 5. 檔頭版本標記（每個制度檔第一段引用區）

```
> 最後更新：YYYY-MM-DD｜原因：一句話
```
只在**語意變更**時更新（錯字修正不用）。不記模型名，記日期與原因就夠了。
豁免：`LESSONS.md` 與其 archive 是 append-only 記錄檔，不需要此檔頭。

## 6. 這套制度自身的健康檢查（每次被 CLAUDE.md 路由到本檔時順手做，30 秒）

- 手上這次修改，是在「解決重複發生的問題」還是「順手覺得可以加」？後者 → 停，進 LESSONS。
- 本次 session 到目前為止：有沒有一條紅線被違反卻沒人發現？有 → 先補記 LESSONS。
