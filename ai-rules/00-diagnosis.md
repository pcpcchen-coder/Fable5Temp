# 00 · Harness 快速診斷：前三名風險與修法

> 最後更新：2026-07-04｜原因：初版（由一次性的較強模型 session 建立）
> 本檔是整套制度的「為什麼」。其他檔案的規則都源自這三條診斷。改任何規則前先回來看這裡。

## 診斷對象

這個環境的長期型態：Claude Code 遠端 session，主模型（多為 Sonnet 等級）擔任指揮官，
可派 subagent（Explore、general-purpose、自訂 agent），容器短命、產出必須 push 才保得住。
repo 本身沒有程式碼，任務多為研究、寫檔、跨 repo 操作、制度維護。

排序依據：發生機率 × 傷害 × 弱模型是否更容易踩。

---

## 第 1 名：主對話被原始資料灌爆（最大的 token 漏，也是失焦的主因）

**症狀**：主模型自己 Read 整個檔案、自己跑多輪 Grep 把結果全吞進對話、自己 WebFetch 整頁網頁。
context 快速膨脹 → 觸發自動摘要 → 任務的驗收條件和早期決策被壓縮掉 →
模型開始重複讀同一個檔、忘記已完成的步驟、偏離原始任務。
弱模型特別嚴重：它們的預設本能是「我自己看一下」，而且摘要後更難重建任務約束。

**修法（具體門檻，不是原則）**：
1. 觸發以下任一條件，一律派 subagent，主對話只收結論（規則見 `10-model-dispatch.md`）：
   - 預期要讀超過 2 個檔案，或單一檔案超過 200 行
   - 搜尋一次 Grep 沒有直接命中，需要換 pattern 再找
   - 任何網頁查詢或文件研究
   - 超過 2 個檔案的修改（超過 5 個檔案時，另須先 1 檔試點，見第 3 名修法）
2. 自己 Read 時一律指定行號範圍；同一個檔案在同一 session 不讀第二次——
   第一次讀完就把結論（含 file:line）記進工作筆記或 todo，之後引用筆記。
3. 超過 3 步的任務，動手前先建 checklist（用環境的任務清單工具；沒有就寫一個
   scratchpad 的 WORKLOG 檔）。context 被摘要後，以 checklist 回錨，不憑記憶。

## 第 2 名：無驗收條件的派工＋自驗宣告完成（誤解任務＋假完成的來源）

**症狀**：派工單只寫「去修 X」，subagent 自行腦補範圍，回報「完成了」，主模型照單全收。
或者主模型自己做完，以「檔案寫出去了／程式碼能編譯」為完成標準，
沒有任何人對照原始需求逐條驗過。弱模型的「完成」判定天生偏鬆，這是它們最貴的一類錯誤：
錯誤產出被 push 出去，下個 session 又基於錯誤產出繼續蓋。

**修法**：
1. 派工三件套強制：目標與動機、可機械判定的驗收條件、固定回報格式。缺一不派。
   （模板見 `30-delegation-templates.md`；缺三件套的反例見 `10-model-dispatch.md` 第 4 節。）
2. 驗證不自驗：實作者不驗收自己的產出。驗收派 fresh-context agent，
   只給驗收條件與產出位置、不給實作過程。檔案用 read-back，程式碼用測試或實跑，
   高風險判斷加第二意見。（流程見 `10-model-dispatch.md` 第 9 節。）
3. 「完成」的定義收斂成一條可查核的 rubric（見 `20-judgment.md` 第 2 節）：
   驗收條件逐條有證據 + fresh-context 驗證 PASS + 已 commit push。三者缺一都不算完成。

## 第 3 名：誤改檔與制度自我增生（單次事故＋長期腐化，合併為一類「不可逆傷害」）

**症狀（短期）**：改錯檔、整檔覆寫掉沒備份的內容、批次修改一口氣改 20 個檔才發現 pattern 錯了。
**症狀（長期）**：CLAUDE.md 和規則檔被歷任 session「順手」加料，越長越大——
每個 session 的固定 token 成本上升，規則開始互相矛盾，弱模型挑錯的那條遵守。
這兩件事本質相同：對「未來所有 session 都會繼承的狀態」做了沒有退路的變更。

**修法**：
1. 改任何既有檔案前，先確認 git 工作區乾淨（`git status`）；不乾淨就先 commit。
   git repo 內，乾淨的 commit 點就是備份。改 git 沒追蹤的檔案（或在非 git 環境），
   先 `cp 檔案 檔案.bak-YYYYMMDD` 再動手。
2. 批次修改先在 1 個檔案上試點，派 fresh-context 驗證通過後，才展開到其餘檔案。
3. CLAUDE.md 硬上限 80 行，只放路由和紅線；內容一律進引用檔。
   規則檔的增生由 `40-maintenance.md` 的精簡觸發條件控制：
   教訓先進 LESSONS.md，同類問題重複發生才升級成規則。
