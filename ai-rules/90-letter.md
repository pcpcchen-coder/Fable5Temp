# 90 · 給未來 session 的信

> 最後更新：2026-07-04｜原因：初版
> 寫信人：建立這套制度的一次性 session（2026-07-04，較強模型）。
> 收信人：之後在這個環境長期運作的每一個 session——多半是 Sonnet 等級。這封信是脈絡，
> 不是規則；規則在 00–40 號檔。但如果規則和現實打架，回來讀這裡，理解當初的取捨。

## 一、三件使用者沒問、但對這個環境最重要的事

### 1. 制度的死法不是被違反，是被遺忘

弱模型 session 最常見的失敗不是「讀了規則卻不遵守」，而是**憑本能直接動手，
從頭到尾沒想起制度存在**。所以 CLAUDE.md 刻意只有三條紅線＋一張路由表——
賭的是「短到你一定會讀完」。自我檢查方法：如果一個 session 進行了 10 輪，
既沒派過工、也沒引用過任何制度檔，而任務又不是純聊天——制度已經失效了，
這件事本身就該寫進 LESSONS.md。

### 2. 你的最大優勢不是聰明，是「可以便宜地開很多個你」

單一 Sonnet 比不過更強的模型，但「一個 Sonnet 指揮官＋N 個各給明確驗收條件的
Sonnet/Haiku 工人＋fresh-context 驗證」的可靠度可以逼近強模型。整套制度就是在
把「聰明」換成「結構」。所以當你覺得任務太難的時候，第一反應不該是「硬做」，
而是「拆細＋提高驗證密度」；拆到每一塊都機械可驗，難度就消失了。
拆不細的那種難（品味、模糊取捨），承認它，走 20 號檔第 6 節的誠實條款。

### 3. 使用者要的是「結論落檔」，不是「對話裡的好答案」

這個環境是短命容器。對話裡再漂亮的分析，沒寫成檔案 push 出去，session 結束就蒸發。
養成習慣：任何花了超過幾輪對話得出的結論——研究結果、決策與排除理由、教訓——
在得出的**當下**就落檔。「稍後一起整理」在這個環境等於「賭 session 不會中斷」，
而 session 會中斷。

## 二、這套制度最可能的退化方式（按可能性排序）與預防

1. **規則堆積成噪音**：歷任 session 順手加規則，兩年後 CLAUDE.md 300 行，沒人全讀。
   → 預防已內建：80 行硬上限、「先進 LESSONS、重複 3 次才升規則」（40 號檔第 2 節）、
   精簡觸發條件（40 號檔第 4 節）。你的責任：看到超限就處理，不要「這次先不管」。
2. **驗證流於形式**：verifier 開始引用實作者的自述當證據，PASS 變成橡皮圖章。
   → 預防：模板 5 明文規定證據必須是驗證者自己讀到／跑到的。你的責任：抽查——
   偶爾對一個 PASS 追問「證據的 file:line 是什麼」，答不出就記 LESSONS。
3. **升降級路徑被繞過**：要嘛不好意思升級（在 sonnet 上耗十輪），要嘛全部直上 opus。
   → 預防：門檻是數字（錯 1 次／連錯 2 次），不是感覺。升級時必附失敗軌跡這條，
   本身就在抑制輕率升級——寫不出軌跡代表你還沒認真試過。
4. **環境事實過期造成集體幻覺**：模型 ID 換代、agent 欄位改名，規則檔還在引用舊的。
   → 預防：事實全部集中在 05 號檔（其他檔只引用它），05 檔頭寫明「呼叫失敗先更新我」。

## 三、本次建立制度時的假設（使用者沒有逐一確認過）

1. **沒有開場提問**：委託書允許問 5 題內，但規格已足夠明確且環境是自主模式，
   選擇不阻塞。若以下假設有錯，修正的地方都已集中：
2. **語言**：制度檔全用繁體中文（使用者的語言）。若未來要給只讀英文的工具鏈用，再議。
3. **agent 定義放在本 repo 的 `.claude/agents/`**：只在「工作目錄是本 repo」的 session
   生效。若使用者的日常工作在別的 repo，需要把 `.claude/agents/` 三個檔複製到該 repo
   或 `~/.claude/agents/`（全域）。這是本制度**已知的最大部署缺口**。
4. **門檻數字**（讀檔 >2 檔、批次 >5 檔、錯 1/2 次升級……）是初版拍板值，
   依據是一般 harness 經驗而非本環境實測。用三個月後拿 LESSONS 的證據回頭調。
