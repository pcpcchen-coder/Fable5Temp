# 20 · 判斷力 rubric（拿不準的時候查這裡）

> 最後更新：2026-07-04｜原因：初版
> 用法：這不是要背的規則，是查表。遇到「該不該升級／算不算完成／該不該問人／
> 該不該換路」的猶豫時，找到對應節，逐條對照訊號，照結論走。
> 每節附一個正例（該這樣）和一個反例（別這樣），對照自己的情況更快。

## 1. 何時該升級模型

**升級訊號（命中任一條就升）**：
- 命中 `10-model-dispatch.md` 第 6 節的失敗門檻（haiku 錯 1 次；sonnet 同一子任務連錯 2 次）
  ——此時升級或換路（本檔第 4 節）擇一，但禁止原樣再試第三次
- 任務需要在多個合理方案間權衡（不是找答案，是做取捨）
- 兩個 subagent 的回報互相矛盾，而你無法用一次事實查核裁決
- 即將做不可逆操作（force push、刪除、對外發佈），而決策依據來自便宜模型的判斷
- 你發現自己在為同一個問題寫第三張派工單

**正例**：sonnet 修一個並發 bug，兩輪都是「修好 A、測試又冒出 B」。
→ 停止第三輪，整理失敗軌跡（兩輪各改了什麼、測試輸出、為何判定失敗），升 opus。

**反例**：haiku 把一個 import 路徑改壞了，主模型心想「小事」，自己下場改，
結果連鎖十幾輪對話都在處理這個檔。→ 正確做法是 haiku 錯的當下直接派 sonnet 一次收掉。

**反升級（同樣重要）**：不要因為任務「感覺重要」就直上 opus。
判準是「需不需要權衡與設計」，不是「重不重要」。重要但機械的事（照清單逐項檢查），
sonnet + 高 effort + 嚴驗收就夠。

## 2. 何時算真的完成

**完成 = 三項同時成立，缺一都不准對使用者說「完成了」：**
1. 派工單（或原始需求）的驗收條件**逐條**有證據
2. fresh-context 驗證 PASS（`10-model-dispatch.md` 第 9 節；純對話性回答除外）
3. 產出已 commit + push（遠端環境沒 push 等於沒發生）

**正例**：「三個檔案已寫入並 push（commit abc1234）。verifier read-back 逐條核對
驗收條件 5/5 PASS，證據見其回報。未解事項：X 查不到官方數據，已在檔內標註。」

**反例**：「我已經把規則加進 CLAUDE.md 了，應該可以了。」——沒有 read-back、
沒有 commit、「應該」二字直接暴露沒驗過。這種話說出口前先回本節第 1 行。

**部分完成要照實說**：完成 7/10 就回報 7/10 加剩餘清單。
把部分完成包裝成全部完成，是本制度裡最嚴重的違規（它會污染下游所有工作）。

## 3. 何時停下來問使用者

**必問（停下手，用一批問題一次問完）**：
- 不可逆**且**超出原始委託範圍：刪除資料、對外發佈、改權限、動到委託沒提的系統
- 需求有兩個以上合理解讀，且不同解讀導致**交付物本質不同**（不是細節不同）
- opus 也連錯 2 次（升級路徑到頂了）
- 發現使用者的前提可能有誤（例如要求修的 bug 其實是另一個系統的行為）

**不問（選預設值、記錄假設、繼續做）**：
- 可逆、且任一合理解讀都能接受（例：檔名怎麼取、段落順序）
- 查得到的事實（環境能查的自己查，查完落檔）
- 純風格偏好且無既有慣例可循 → 選常見做法，在產出中標註「假設：…」

**正例**：任務是「清掉過時的規則檔」，但其中一檔看起來還被引用。
→ 停，問：「A 檔仍被 B 引用，要一起改 B 還是保留 A？」（不可逆 + 兩種合理解讀）

**反例**：為了「報告用什麼標題格式」暫停整個任務等使用者回覆八小時。
→ 可逆、任何合理格式都行：選一個、標註假設、繼續。

**問的品質**：一次集中問完（最多一批 5 題內），每題附上你建議的預設選項。
問「A 還是 B？我建議 A，因為…」，不要問「你覺得呢？」。

**必問、但使用者不在場**（自主／排程 session）：不要替使用者做必問級的決定。
停下該子任務，把問題與你的建議落檔（LESSONS.md，或 `90-letter.md` 第四節的交接區），
繼續做不受阻塞的其他部分。

## 4. 方向錯了的訊號（換路，而不是重試）

重試 = 同方法再來一次。換路 = 換方法、換切入點、或收窄範圍重定義問題。

**換路訊號（命中任一條，禁止原樣重試）**：
- 同一個錯誤換了措辭再出現第二次
- 修好 A 壞了 B，修好 B 又壞了 A（蹺蹺板循環）
- 每前進一步都需要一個新的特例補丁（方案在跟你討價還價）
- 你開始改動與原任務無關的檔案「好讓它動起來」
- 你發現自己在懷疑工具壞了（多半不是工具壞了，是用法或前提錯了）

**重試合理（原地再試不算浪費）**：
- 錯誤訊息每次不同**且在收斂**（錯誤越來越接近表層）
- 環境暫時性失敗：網路逾時、rate limit、容器抖動

**正例**：批次改 20 個檔的腳本，前 3 個檔各需要一個不同的特殊處理。
→ 停：pattern 假設錯了。回頭重新分類這 20 個檔，而不是繼續為第 4 個寫特例。

**反例**：測試失敗，訊息一字不差，連續重跑三次「看看會不會過」。
→ 同樣輸入同樣輸出，重跑不會變。第二次失敗就該去讀失敗原因或派人查。

## 5. 品質底線怎麼驗（依產出類型）

- **制度檔/文件**：讀者測試——派一個零脈絡的 fresh agent 只讀該檔，要求它回答
  「這檔要我在什麼情況下做什麼？」複述錯誤或答不出 → 檔案不合格，改到複述正確為止。
- **程式碼**：測試綠 + 至少一條真實執行路徑跑過 + diff 只含任務相關變更（多餘的改動
  是品質缺陷，不是順手幫忙）。
- **研究/報告**：每個關鍵論斷有來源；「查證過」與「推測」分開標；查不到的寫「查不到」。
- **決策**：寫得出「排除了哪些替代方案、為什麼」才算有品質；只有結論沒有排除理由的
  決策，視為未完成。

**正例**：制度檔改完，fresh agent 複述時把「錯 2 次升級」說成「錯了就升級」。
→ 抓到歧義，把原文改成「同一子任務**連續**錯 2 次」再驗一次。

**反例**：「文件我讀了一遍覺得沒問題」——作者自讀不構成品質證據（見 10 號檔第 9 節）。

## 6. 誠實條款：這套 harness 補得了什麼、補不了什麼

**補得了（用拆解＋驗證＋多樣本評審）**：執行品質——漏步驟、看錯檔、假完成、
機械性錯誤。這些靠制度能把弱模型拉到接近強模型的可靠度。

**補不了：模糊題與品味判斷。** 例如：兩個都說得通的產品方向、文案的語感、
架構取捨中「十年後哪個好維護」這類無法驗證的判斷。rubric 能過濾爛答案，
無法從幾個像樣的答案裡挑出真正對的那個。

**遇到補不了的怎麼辦（按序）**：
1. 升到可用的最強模型，產 2–3 個帶理由的候選方案（不是一個）
2. 交使用者選，明說「這是品味/賭注判斷，制度給不了保證」
3. 使用者不在場且必須前進 → 選最可逆的那個方案，把選擇理由與回退路徑落檔

**禁止**：假裝 rubric 分數能決定品味題；把「多數 agent 投票的結果」包裝成「正確答案」。
投票只證明答案不爛，不證明答案對。
